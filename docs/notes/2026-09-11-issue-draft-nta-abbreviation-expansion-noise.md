# issue 草案: 通称の OR 展開で、キーワードを含まない条項が検索結果に混ざり、含む条項が押し出される

対象リポジトリ: houki-nta-mcp（2026-09-11 作成）
提出先: https://github.com/shuji-bonji/houki-nta-mcp/issues
起票済み: https://github.com/shuji-bonji/houki-nta-mcp/issues/21 （2026-09-11）
タイトル案: 通称（適格請求書発行事業者・軽減税率など）の OR 展開で、キーワードを含まない条項が上位に混ざり、含む条項が結果から外れる

---

## 前提条件（どの版で起きるか）

- **公開版で再現します。** Claude の plugin 経由の houki-nta（`nta_search_tsutatsu` の説明に v0.10.1 で入った `search_notes` の記述があり、応答に v0.11.0 候補の `base_laws` が無い版）で、2026-09-11 に確認しました。
- **開発版（v0.10.4 + Issue #20 の変更）でも同じ結果です。** Issue #20 の変更は検索の条件と並べ替えに触れていません。
- **原因のコードは v0.9.2 で入り、v0.10.0 以降も変わっていません。** `src/services/db-search.ts` の `EXPAND_FORMAL_FOR_HINTS` に `houki-egov` を加えたのが v0.9.2（Issue #14、コミット 3db8d94）です。v0.10.0（コミット cd5dada）の同じファイルにも同じ定義があります。v0.10.1 の変更（Issue #18）は 3 文字未満の語の扱いだけです。
- 通称の定義は houki-abbreviations 0.4.1（houki-nta-mcp の依存は `^0.4.1`）の「消費税法」エントリの `aliases` です。`適格請求書発行事業者` のほか、`インボイス`・`適格請求書`・`軽減税率`・`簡易課税` などが含まれます。

## 再現手順

ローカル DB を `--bulk-download-everything` で作ったうえで、次の 2 つを比べます。

1. `nta_search_tsutatsu` に `{ "keyword": "適格請求書発行事業者", "limit": 30 }`
2. `nta_search_tsutatsu` に `{ "keyword": "請求書発行事業者", "limit": 50 }`

2 は通称の辞書に無い語なので展開されません。trigram の部分一致なので、1 の語を含む条項をすべて返します。

## 観察結果

| | 1（展開あり、limit 30） | 2（展開なし、limit 50） |
| --- | --- | --- |
| 返った件数 | 30 | 32 |
| 「適格請求書発行事業者」を含む条項 | 23 | 32（すべて消費税法基本通達） |
| 含まない条項 | 7 | 0 |

- **含まない 7 件**: 6-6-3・6-8-3・6-10-4・6-7-10・5-8-1・15-2-1・4-4-1。どれも本文に「消費税法」が出てくるだけの条項です（6-6-3 は「厚生労働省告示第7号『消費税法別表第二第6号…』」、4-4-1 は「…の者とみなして消費税法が適用される…」）。
- **押し出された 9 件**: 1-8-15・16-2-8・11-1-8・11-1-7・11-6-8・11-6-7・15-2-1の2・11-5-3・1-4-6。語を含むのに 1 の結果に入りませんでした。
- **並び順も混ざっています。** 含まない 6-6-3（score 0.3799）が、含む 1-7-1（0.3797）・16-2-6・1-8-2・1-4-1 などより上に来ています。
- **どの hit が展開で拾われたかが応答から分かりません。** `scoreReasons` の `abbreviation expanded: 適格請求書発行事業者 → 消費税法` は、語を含む hit にも含まない hit にも同じように付いています。

## 原因

1. `buildFtsQueryWithAbbreviation()` は、キーワードが houki-abbreviations のエントリ（`source_mcp_hint` が `houki-nta` か `houki-egov`）に解決されると、`("適格請求書発行事業者") OR ("消費税法")` という FTS5 の式を作ります。消費税法基本通達の本文には「消費税法」がほぼどの条項にも出てくるため、OR の右側だけで多数の条項が当たります。
2. 並べ替え（`computeRelevance()`）は FTS5 の rank と文書種別の重みしか見ていません。元のキーワードを本文やタイトルに含むかどうかで点を上げる処理はありません。v0.9.2 の CHANGELOG には「Phase 6-1 の re-rank で『インボイス』自体を含む文書が score 上位に並ぶ」とありますが、コードにはその処理がありません。
3. v0.9.2 の展開は「インボイス」のように**通達の本文に出てこない通称**で 0 件になる問題（Issue #14）を解くためのものでした。「適格請求書発行事業者」「軽減税率」のように**本文にそのまま出てくる語**でも同じように展開するため、ヒットが十分にあるのに OR 側の条項が混ざります。

## 影響範囲

- `nta_search_tsutatsu`（`searchClauseFts()`）で上のとおり確認しました。
- 改正通達・事務運営指針・文書回答事例・タックスアンサー・質疑応答事例の検索（`searchDocumentFts()`）も同じ `buildFtsQueryWithAbbreviation()` を通ります。コード上は同じことが起きますが、実測はしていません。
- limit を上げれば押し出された条項は戻りますが、利用者（LLM）には「結果が 30 件で打ち切られたのか、全部なのか」「どれが展開で拾われたのか」を判断する材料がありません。

## 対応案

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | 元のキーワードで 0 件のときだけ展開する | Issue #14 の目的（通称で 0 件になる）をそのまま満たし、それ以外は展開前と同じ結果になる | 元の語で 1〜数件しか当たらないときに、展開で広げる機会を失う |
| B | 元のキーワードで当たった条項を先に並べ、limit に満たないときだけ展開で当たった条項を後ろに足す | 元の語を含む条項が押し出されなくなる。少数ヒットのときも広げられる | 検索を 2 回流す |
| C | 展開は今のまま、元のキーワードを含む条項の score を上げる | 変更が並べ替えだけで済む | 含まない条項が limit 内に残ることがある（語を含む条項が limit より多いときも混ざる） |

どの案でも、hit ごとに「元のキーワードで当たったか / 展開で当たったか」を返すことを提案します（例: `matched_by: "keyword" | "expansion"`）。いまの `scoreReasons` は全 hit に同じ文言が付くため、区別に使えません。

A か B を推奨します。A は変更が小さく、B は少数ヒットの場合も扱えます。

## 確認すること

- `searchDocumentFts()` 側（質疑応答事例・タックスアンサーなど）でも同じ比較をして、影響を実測する。
- 「インボイス」のように本文に出てこない通称で、案 A・B が Issue #14 の解決（0 件にならない）を保つことをテストで確かめる。
- v0.9.2 の CHANGELOG の「re-rank で上位に並ぶ」という記述を、実装に合わせて直すか注記する。
