# 作業手順: ローカル DB の説明を、共通部分と MCP ごとに分ける

作成日: 2026-09-12 / 対象: houki-hub の site
前提: [PR #13](https://github.com/shuji-bonji/houki-hub/pull/13) でマージ済みの `/guide/local-database` を書き直す

---

## なぜ書き直すか

公開した `/guide/local-database` に、次の指摘を受けました。

1. `search_fulltext` が「DB が無いと使えない」と読める。実際はツールは動き、中身が別のものに替わる
2. 「DB 無しのとき」が曖昧。「DB を作っていない状態」なのか分からない
3. データのライフサイクル（元データが変わったときに何が起きるか）の図が無い
4. 「取得と検索は別のコマンドです」は分岐も流れも無いので、図ではなく表にすべき
5. houki-egov-mcp と houki-nta-mcp の DB が同じものに見える。実際は別

## 調べて分かったこと（書き直しの根拠）

**2 つの DB は目的が違います。** 共通なのは実装の方針だけです。

| | houki-egov-mcp / `laws.db` | houki-nta-mcp / `cache.db` |
| --- | --- | --- |
| **役割** | 公式一括データの写しと、全文検索の索引 | 国税庁サイトを構造化した唯一の形 |
| **DB が無いと** | 全文検索だけが使えない（他は API で動く） | 検索も一部の取得もできない |
| 取得元 | e-Gov 配布の全件 zip（約 290 MB）1 本 | 国税庁の HTML を 1 ページずつ |
| DB が要るツール | 7 つ中 1 つ（`search_fulltext`） | 14 つ中 9 つ |
| 単位 | `law_revision_id`（法令の**版**） | 通達は 章→節→条、文書は `doc_type`/`doc_id` |
| テーブル | `laws` `articles` `revisions_meta` `sync_state` | `tsutatsu` `chapter` `section` `clause` `document` |
| 鮮度の持ち方 | `sync_state`（DB 全体で 1 行） | 行ごとの `fetched_at` |
| 更新の粒度 | 全件のみ（差分同期は未実装） | 節・文書ごと（`content_hash` 比較、`--refresh-stale`） |
| 元データが変わると | `content_hash` が変わった版だけ入れ直す。古い版は残るが、検索は現行版に絞る | 4 分類（新規 / 更新 / 索引から消えた / 移動の推定）。消えた文書も残り、**印が無いので検索に出る** |
| 版が上がったとき | 取り直しの案内 | スキーマ移行（v0.15.0 は起動時に自動で入れ直し） |

共通しているのは 4 つだけです。

- 取得は MCP サーバーとは別のコマンドで行う（サーバーは勝手に取得しない）
- SQLite + FTS5 の trigram tokenizer を使う
- 正規化を `@shuji-bonji/houki-abbreviations` で揃える
- `freshness` のしきい値が同じ（7 日 / 30 日）と、置き場所の規約（`XDG_CACHE_HOME`）

`cache.db` という名前は実態を言い当てていません。キャッシュなら古いものを捨てますが、消えた文書を保持し、移動を推定し、構造変質を検知します。改名は既存利用者の DB パスが変わるので勧めませんが、**ページで「キャッシュ」と書かない**ようにします。

## 書き直す形

### `/guide/local-database`（174 行 → 60 行程度）

共通部分だけに絞ります。

1. なぜローカル DB があるのか（1 段落）
2. **必須ではない**こと
3. 取得と検索は別のコマンド（**表**にする。今の Mermaid は削除）
4. **2 つの DB の違いの比較表**（上の表。役割を先頭に置く）
5. 共通していること（FTS5 trigram / 正規化 / `freshness` のしきい値 / 置き場所の規約）
6. 各 MCP ページへの導線

### `/mcp/houki-egov` の「全文検索のためのローカル DB」節を拡充

- 役割（公式一括データの写し + 全文検索の索引）
- **DB を作っていないとき何が起きるか**: `search_fulltext` は呼べて応答も返る。ただし条文本文の検索ではなく法令名の一致検索になり、`source: "api-fallback"` が付く。`get_law` など他の 6 ツールは DB を見ないので影響なし
- 作り方（`--bulk-download-everything`、zip 約 290 MB）
- **ライフサイクル図**（取得元 → 取り込み → 検索 → 元データが変わる → 変わった版だけ入れ直す → 古い版は残るが検索には出ない）
- `--status` の見方
- 差分同期は未実装（`--bulk-download-by-date` はデバッグ用）
- 置き場所（`laws.db`、`HOUKI_EGOV_DB_PATH`）
- 版が上がったとき（v0.5.0 / v0.5.1 は取り直し）

### `/mcp/houki-nta` の「ローカル DB の作り方」節を拡充

- 役割（国税庁サイトを構造化した唯一の形。API が無いこと）
- **DB を作っていないとき何が起きるか**: 検索 6 つは `DOC_NOT_FOUND`。取得は 3 通りに分かれる（現状の表と [#29](https://github.com/shuji-bonji/houki-nta-mcp/issues/29) への導線。既存の警告ブロックを移す）
- 作り方（種別ごとの時間の表、税目での絞り込み）
- **ライフサイクル図**（取得元 → 1 ページずつ → 4 分類 → 消えた文書も残る）
- 元データが変わったときの 4 分類の説明と、**索引から消えた文書が現行と区別できない**こと（別途 issue 草案あり: `2026-09-12-issue-draft-nta-orphaned-docs.md`）
- 「構造変質の疑い」の警告が何を意味するか
- 更新（`--refresh-stale=N` → `--apply`、`--refresh`）
- 置き場所（`cache.db`、`--db-path`、`HOUKI_NTA_DB_PATH`）
- 版が上がったとき（v0.15.0 の自動移行）

## 書くときの注意

- 「DB 無しのとき」→「ローカル DB を作っていないとき」
- 「キャッシュ」と書かない
- 「DB が無いと使えない」と書かない。**何ができなくなるか**を書く
- ライフサイクル図は 2 つ別々にする。粒度も更新方法も違うので 1 つにまとめない
- 図にするのは分岐や流れがあるものだけ。並びを示すだけなら表にする
- 所要時間は `--help` の記載を使う。egov の実測時間は不明なので書かない（zip のサイズだけ書く）
