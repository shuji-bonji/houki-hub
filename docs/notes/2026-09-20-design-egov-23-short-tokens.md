# 設計メモ: 2 文字語の本文検索をどう扱うか（egov#23）

対象リポジトリ: houki-egov-mcp（`houki-hub/mcp/houki-egov-mcp`、2026-09-20 JST 作成）

出典: [egov#23](https://github.com/shuji-bonji/houki-egov-mcp/issues/23) / houki-hub#20 の機能 7 / houki-hub#21

## 1. 何が起きていたか

`search_fulltext` に「相殺」だけを渡すと、返ってくるのは次の 1 件だけでした。

```jsonc
{
  "keyword": "相殺",
  "source": "bulk",
  "count": 1,
  "hits": [
    { "match_type": "law_meta", "law_title": "相殺関税に関する政令", "article_num": null, "score": 0.09 }
  ]
}
```

条本文の索引 `articles_fts` は `tokenize = 'trigram'` なので、3 文字以上の語しか索引に載りません。2 文字の「相殺」は `MATCH` 式が空になり、条の本文はまったく引かれていません。返っているのは `laws.law_title` を LIKE で照合した法令名ヒットだけです。

問題は 2 つありました。

1. 民法 505 条（相殺の要件）にたどり着けない
2. 条の本文が引かれなかったことが、応答のどこにも書いていない。`match_type: "law_meta"` は 1 件ごとの値で、「本文を引いた結果 0 件だった」のか「本文を引いていない」のかを区別しない

Issue の完了条件は 2 のほうです。

## 2. 索引から 2 文字語に届く道があるか

先に、索引を使う方法が無いかを確かめました。SQLite 3.53 の FTS5 で、trigram 索引を張った小さなテーブルに対して試した結果です。

| 試したクエリ | 結果 |
|---|---|
| `MATCH '"相殺"'` | 0 件 |
| `MATCH '相殺*'`（前方一致） | 0 件 |
| `MATCH '"相殺" *'` | 0 件 |
| `MATCH '対当額について相殺'`（3 文字以上） | ヒット |

前方一致なら「相殺◯」という trigram を拾えるのではないかと考えましたが、クエリ側も同じ trigram で分割されるため、2 文字では分割結果が空になり 0 件です。索引の側から 2 文字語に届く道はありません。

Issue の選択肢 2（bigram トークナイザ）は、1 文字ごとに区切り文字を挟んだ列をもう 1 本持てば trigram で代用できます（「相殺」→「相␟殺」で 3 文字）。ただし本文 588 MB が 1.18 GB になり、その上に trigram 索引がもう 1 本載ります。DB の大きさに見合わないので採りませんでした。

## 3. 索引を使わない走査にいくらかかるか

実データ（条 1,434,710 件・法令 10,810 件・本文 587,926,852 バイト）で測りました。

| 測り方 | 最悪値（該当ゼロで全表を走り切る） |
|---|---|
| `LIKE` + JOIN | 12.07 秒（キャッシュが温まった状態）／ 21.99 秒（冷えた状態） |
| `instr` + JOIN | 21.99 秒 |
| `GLOB` + JOIN | 22.20 秒 |
| `instr`、JOIN 無し | 21.79 秒 |

| 上限 150 件で打ち切れる語 | 所要時間 |
|---|---|
| `LIKE` 「相殺」 | 5.49 秒 |
| `LIKE` 「善意」 | 4.08 秒 |
| `instr` 「相殺」 | 5.40 秒 |

`body` は投入時に正規化済み（小文字化・幅の統一）なので、`LIKE` の大文字小文字の同一視は不要です。そこで `instr`（素の部分文字列検索）と `GLOB` も測りましたが、3 つとも 22 秒で並びました。JOIN を外しても同じです。費やしているのはパターン解釈でも JOIN でもなく、588 MB を読んで端から照合する分そのもので、書き方では縮みません。

打ち切りが効く語でも 4〜5 秒かかります。MCP のツール呼び出しの既定として、この値は受け入れられません。

## 4. 決めたこと

**既定では走査せず、`scan_body: true` を付けたときだけ走査する。** 走査するかどうかに関わらず、何をして結果を出したかを `short_tokens` で申告する。

`body_search` は、実際に走った経路の名前をそのまま値にします。

| クエリ | `body_search` | 何をするか | 速さ |
|---|---|---|---|
| `適格請求書 保存` | `fts_then_filter` | 3 文字以上の語で索引を引き、その条の本文に 2 文字語が含まれるかで絞る | 索引を使う |
| `労基法 協定` | `like_in_law_scope` | 法令名で対象法令を絞り、その範囲の条の本文を引く | 対象が絞れている |
| `相殺` | `not_searched` | 条の本文は引かず、法令名・略称・番号の照合だけを返す（既定） | 走査しない |
| `相殺` + `scan_body: true` | `like_all_articles` | 索引を使わず、全法令の条の本文を端から照合する | 5〜20 秒 |

`not_searched` のときは `next_actions` に 2 つの形を入れます。

1. `{ keyword: "民法 相殺" }` — 法令名を添えると、その法令の条に絞って索引で引けます
2. `{ keyword: "相殺", scan_body: true }` — 法令名が分からないときの最後の手段

`hits_by_match_type` に `article`（条本文由来）と `law_meta`（法令名・略称・番号由来）の件数を入れます。Issue の完了条件「結果が本文由来か法令名由来かが応答から分かる」は、この 2 つの数で答えます。

## 5. 走査の書き方

`searchArticleLikeGlobal` には `ORDER BY` を付けません。並べ替えると SQLite は必ず全表を読みますが、付けなければ `LIMIT`（150 件）に達した時点で走査を止められます。「相殺」が 5.4 秒で済むのはこの打ち切りが効いているからで、`ORDER BY a.ord` を付けると 22 秒になります。

そのかわり並び順は関連度順ではなく DB 内の順になります。`short_tokens.note` に「並び順は関連度順ではありません」と書き、上限に達したときは `truncated: true` を立てます。

`rank` は固定 `-5.0` です。`relevance-scoring.ts` の `rankToBaseScore` で base が 0.33 になり、法令名ヒットの固定 `rank -1.0`（base 0.09）より上に来ます。本文を求めて呼ばれているので、条のヒットが法令名のヒットより上に並びます。

## 6. ついでに直したこと

LIKE 経路の `snippet` を、本文の先頭 80 文字から「一致位置の手前 20 文字からの 80 文字」に変えました（`substr(a.body, max(1, instr(a.body, ?) - 20), 80)`）。既存の `searchArticleLikeInScope`（「労基法 協定」の経路）も同じ式に寄せたので、そちらでも一致した箇所が snippet に入るようになります。FTS の `snippet()` は `MATCH` にしか使えないため、LIKE 経路では自前で切り出します。

## 7. 残したこと

- 2 文字語での関連度順の並べ替えはできません。走査は打ち切りが前提なので、全件を見てから並べることができません
- bigram 索引（3 節）は採りませんでした。DB の大きさが 2 倍近くになります。2 文字語の検索が主要な使い方になるようなら、そのときに測り直します
