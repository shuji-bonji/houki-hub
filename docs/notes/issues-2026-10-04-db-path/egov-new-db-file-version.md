## 何が起きるか

0.18.x 以前の houki-egov-mcp は、版が違う DB を開くと全テーブルを消して作り直します。そのため、0.19.0 で作り直した DB（版 3）を 0.18.x 以前の CLI か MCP サーバーで開くと、約 290 MB の取り込みが消えます。0.19.0 の CHANGELOG の冒頭で注意していますが、0.19.0 の側では防げません（古い版の動きのため）。

起きうる経路:

- plugin の版が固定されている環境、または `npx` のキャッシュに古い版が残っている環境
- 手元のビルドを起動するサーバー（`claude_desktop_config.json` に手で書いたもの）で古いコミットを試したとき
- 同じ DB を、版の違う 2 つの MCP クライアントから開いたとき

0.19.0 からは、新しい版・読めない版の DB はどの入口も書き換えません（SPEC-EGOV-DB-SCHEMA-025）。したがって、**次に DB の版を上げるとき（版 4）は、0.19.0 以降が版 4 の DB を消すことはありません。** 一方で、版 3 の DB を版 4 のサーバーで開くと「古い版」として扱い、`--bulk-download-everything` での作り直しが要ります。

## 提案

DB の既定のファイル名に DB の版を入れる（例: 版 4 から `laws.v4.db`）。

| | 長所 | 短所 |
| --- | --- | --- |
| ファイル名に版を入れる | 版の違う houki-egov-mcp が同じファイルを開かない。古い版のサーバーが残っていても、新しい DB に触れない。新しい版を試しても、元の DB が残る | DB の版を上げるたびに、新しいファイルへの取り込み（約 290 MB、5 GB 前後）が要る。古いファイルが残るので、消す案内が要る。`HOUKI_EGOV_DB_PATH` を設定している利用者には効かない |
| 今のまま（`laws.db`） | ファイルが 1 つで分かりやすい | 版をまたぐ事故は、0.19.0 以降どうしの組み合わせなら起きないが、版 3 → 4 の作り直しで元の DB を上書きする |

2026-10-04 JST に shuji の環境で、`HOUKI_EGOV_DB_PATH` で `laws.v3.db` を別に作って試し、確かめた後に `laws.db` へ名前を変えて切り替えました（取り込み直しは不要でした）。ファイル名に版を入れる案は、この手順を既定にするものです。

## 決めること

1. 次に DB の版を上げる版で、既定のファイル名に版を入れるか（今すぐは変えない。版 3 のままファイル名だけ変えると、全利用者が取り込み直しになるため）
2. 入れる場合、前の版のファイル（`laws.db` / `laws.v3.db`）を見つけたときに何をするか: 何もしない / `--status` と DB の場所を確かめるコマンドで知らせる / 版が同じなら移す
3. 入れない場合、版を上げる開発のときは `HOUKI_EGOV_DB_PATH` で別のファイルを使う、という手順を CONTRIBUTING.md に書くだけにするか
4. houki-nta-mcp（既定 `cache.db`、版 12）と同じ方針にするか
