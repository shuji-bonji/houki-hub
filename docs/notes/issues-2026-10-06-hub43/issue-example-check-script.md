# 呼び出し例を同じ引数で流し、例と同じ応答が返るかを機械で確かめる（契約の確認のスクリプト）

houki-hub#43 の追記（2026-10-06 JST）で挙げた隙間を埋めるための Issue です。公開のたびに LLM が手で行っている「契約の確認」を、スクリプトで回せるようにします。置き場所は計画書 `docs/notes/2026-10-04-plan-stage6-and-followups.md` の段階 4、houki-hub#5 ② の近く（作業 6f）です。

## 目的

呼び出し例（`scripts/reference-examples/<server>/ja/*.md`）は、リファレンスのページの材料であると同時に、公開のたびに流す e2e のテストケースとしても使っています。このテストを機械で回し、次の 3 つを実現します。

1. patch の公開でも、変えていないツールの例を含めて全例を流す
2. 例が述べている形と主張が今も成り立つ例（「一致」）は、人と LLM が見なくて済む
3. 「一致」を確かめた版を例に書き戻し、`check-example-versions.mjs` と `stack-check.yml` の Issue がそれを読む（計画書の Q14 の案 B）

## やること

### 1. スクリプト（`scripts/check-examples-contract.mjs` の案）

- 例を読む: `**引数**` の JSON、抜粋の JSON（`**返る JSON**`）、前提の行（`- ローカル DB:`、`- 版の照合: しない` など）
- MCP を stdio で起動して、例の引数でツールを呼ぶ。起動の仕組みは `generate-reference.mjs` の `REGISTRY` と stdio のクライアントを使い回す（hub#5 ② で `npx -y @shuji-bonji/<pkg>@latest` に切り替えるのと同じ仕組み）
- 部分一致で比べる（下の「比べ方の規則」）
- 結果を一致・データ側の差分・形の違い・未確認に分けて、表（Markdown）と JSON で出す

### 2. 比べ方の規則

例の JSON を「部分一致のパターン」として読む。

| 例の書き方 | 比べ方 |
| --- | --- |
| 書いてあるキー | 応答に存在すること |
| 書いてある値 | 同じであること（下の「毎回変わる値」を除く） |
| `"…"`・`/* … */`・途中で切った配列 | どんな値でもよい（配列は、書いてある要素が先頭から同じ順で並ぶこと） |
| 例に無いキーが応答にある | 失敗にせず、「フィールドが増えた」として報告する |

毎回変わる値は、JSON のパスの一覧をスクリプトに 1 か所置き、family で共通にする。

| 種類 | 例 | 比べ方 |
| --- | --- | --- |
| 呼び出しのたびに変わる | `retrieved_at`、`meta.at` | 比べない（値があることだけ） |
| 取り込みのたびに変わる | `fetchedAt`、`freshness.oldest_fetched_at`・`newest_fetched_at`・`days_since_oldest` | 比べない（日時の形であること） |
| 環境で変わる | `freshness.db_path`、保存先の絶対パス | 比べない（`~` で始まるなどの形） |
| 国税庁・e-Gov のページの更新で変わる | 本文の文字列、`effectiveDate`、PDF の大きさ | 違いを「データ側の差分」として報告する。失敗にしない |
| 本文の長さで少し動く | `score`、2 件目以降の順 | 幅を持たせる（例: score は ±0.01、順は 1 件目だけ固定） |

例ごとの例外は、例の冒頭に `- 照合:` の行で書く（例: `- 照合: score は見ない`、`- 照合: 前提 DB に No.2882 の索引から消えた行`）。

### 3. 例を揃える（一度だけ）

48 例の抜粋の JSON と前提の行を、上の規則で読める形に揃える。今の `"…"` と `/* … */` はそのまま使える見込みで、主に直すのは前提の行の書き方。

### 4. 確かめた版の書き戻し（Q14 の案 B）

- 「一致」の例に `- 確かめた版: vX（YYYY-MM-DD）` の行をスクリプトが書く
- `check-example-versions.mjs` は、「実測」と「確かめた版」の新しいほうを `published` と比べる
- 表示の「古い」を、版番号を比べただけだと分かる名前（例: 「前の版で実測」）にする
- `stack-check.yml` の Issue は、`stack.json` のずれと、確かめていない例を分ける

### 5. 公開の手順に組み込む

MCP の公開の後（patch を含む）に、このスクリプトを流す。「形の違い」と「データ側の差分」の例だけを人と LLM が見て、例を書き直すか Issue にする。

## 進め方

1. nta の 1〜2 ツール（`nta_get_tax_answer`・`nta_search_tax_answer`）だけで動かし、比べ方の規則を固める
2. 全例に広げ、例を揃える
3. 確かめた版の書き戻しと `check-example-versions.mjs` の変更
4. 公開の手順と `stack-check.yml` の変更
